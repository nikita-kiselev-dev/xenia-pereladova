## 1. Принятые решения и границы

- Основной skill — `clone-website` от Julian Romli. Дополнительные — `frontend-design` и `webapp-testing` от Anthropic. Все три установлены и прочитаны при подготовке этого плана.
- Предлагаемый стек: **Vite + TypeScript + обычные CSS/DOM**, **GSAP**, **Lenis**, **Three.js** для WebGL-деформации. Версии выбрать и закрепить lockfile при начале реализации.
- Воспроизводить измеренные layout и поведение референса; визуальные решения не заменять типовым шаблоном портфолио.
- Допущение: итоговый сайт посвящён Xenia и использует её фотографии, имя, тексты и контакты. Эти материалы пока не предоставлены. Чужие клиентские списки, награды и биографию не переносить.
- Допущение: первый релиз — портфолио с переходом в почту или предоставленную социальную сеть. CMS, обработчик заявок, оплаты, аккаунты, аналитика и многоязычность в первый релиз не входят.
- Референс задаёт дизайн и motion. URL и внутреннее устройство приложения допускается адаптировать к статическому хостингу.
- В текущей папке найден пустой Git-репозиторий без commits и прикладных файлов. Готового scaffold и действующей сборки нет; проверять `npm run build` сейчас не на чем.

На этапе подготовки работа была ограничена документацией и установкой выбранных skills. Далее сохранён исходный план действий; фактическое выполнение перечислено выше и в QA-отчёте.

### Как адаптирован основной skill

Из [инструкции clone-website](https://github.com/julianromli/ai-skills/blob/0a306e3202ea5de43beac741563f09e6789633e0/skills/clone-website/SKILL.md) применены исследование через браузер, разделение внешнего вида и взаимодействий, фиксация нескольких состояний и подготовка проверяемых спецификаций.

Его предположение о готовом Next.js + shadcn + Tailwind scaffold заменено предложенным минимальным стеком. Немедленная разработка и запуск builder agents не выполняются: пользователь запросил план. При реализации сначала подготовить основу и спецификации; распараллеливать только независимые части при реальной пользе. Фотографии и branding для публикации брать из материалов Xenia; референсные assets учитывать в исследовании отдельно.

`frontend-design` применён к плану токенов и визуальной проверки. `webapp-testing` прочитан и включён в будущие проверки; browser-тесты локального сайта сейчас не запускались. Дополнительно использованы доступные `research`, `skill-installer` и `ponytail` для проверки источников, установки и ограничения зависимостей.

Отдельный `agent-browser` не устанавливался: доступный встроенный браузер уже позволяет исследовать референс. `ui-ux-pro-max` пока не нужен: палитра и композиция заданы выбранным сайтом.

P0 — без этого релиз не считается выполненным. P1 входит в план, реализуется после рабочего основного сценария. Точный вид Intro и фильтров уточняется по полному исследованию.

Маршруты первого релиза: `#/overview`, `#/list`, `#/project/<slug>`, `#/info`. При необходимости фильтр хранить в hash-параметре. При обязательном требовании clean URLs отдельно выбрать статическую генерацию HTML для каждой серии.

## 5. Стек и владение состоянием

| Решение | Назначение | Ограничение |
|---|---|---|
| Vite + TypeScript | Dev server, сборка, типы данных и состояния | Зафиксировать Node и dependencies после проверки совместимости |
| CSS custom properties, Grid, Flex | Токены и responsive layout | Без второго набора токенов для canvas |
| GSAP | Timeline переходов и DOM-анимации | ScrollTrigger подключать для подтверждённых scroll-сценариев |
| Lenis | Инерционная прокрутка | Включать после базовой прокрутки; один источник progress и кадров |
| Three.js + custom shader | Canvas с геометрической деформацией фото | Один renderer; DOM остаётся источником семантики и данных |
| Локальный TypeScript manifest | Серии, изображения, подписи, категории | Без CMS и внешнего API в первом релизе |
| Browser automation / Playwright | Smoke и визуальные сравнения | Успех сборки не заменяет визуальную приёмку |

React/Next.js, Tailwind, shadcn, готовый slider, глобальный state manager и React Three Fiber пока не добавлять: для нескольких представлений и одного canvas они не дают установленной пользы. Если полный разбор выявит конкретную потребность, пересмотреть только затронутое решение.

Минимальные состояния приложения: текущий маршрут, представление галереи, фильтр, выбранная серия, позиция прокрутки и фаза перехода. Разделить запрошенный маршрут и завершённый переход. Повторный click или Back во время animation должен вести в последнее выбранное состояние, не оставляя заблокированный экран.

DOM и canvas используют один manifest и одни измеренные прямоугольники. Обработчики ввода имеют одного владельца; renderer отвечает за drawing, а не за отдельную логику маршрутов. Ресурсы, listeners и timelines освобождаются при смене режима. На touch нет зависимостей от hover.

## 6. Этапы реализации

### Этап 1. Полный разбор референса

**Skills:** `clone-website`, встроенный браузер. **Оценка:** 1–2 рабочих дня.

1. Снять одинаковые состояния на 1440×900, 768×1024 и 390×844; дополнительно проверить 1920px и ширину 320px. Это исследовательские viewport, не готовые CSS-breakpoint.
2. Пройти главную сверху вниз: медленный и быстрый scroll в обе стороны, остановка движения, затем hover и clicks. Проверить каждый режим, фильтр, серию, Close, Back/Forward и resize.
3. Собрать computed CSS: цвета, размеры, line-height, font-weight, spacing, aspect ratio, object-position, z-index, overflow. Определить реальные точки смены layout.
4. Для canvas фиксировать до/во время/после движения, направление, скорость и форму. Записать короткие видео при доступности инструмента; screenshots недостаточно для сравнения динамики.
5. Составить карту контента и assets, источники шрифтов и список недоступных измерений. Числа с измерением отличать от визуальных оценок.

**Будущие артефакты:** `docs/research/BEHAVIORS.md`, `docs/research/PAGE_TOPOLOGY.md`, `docs/research/design-tokens.json`, `docs/research/assets-manifest.json`, `docs/design-references/` и небольшие specs в `docs/research/components/`.

**Выход:** у каждого эффекта известны trigger, начальное/конечное состояние, mobile-вариант и способ проверки; непроверенное отмечено отдельно. До этого не фиксировать точные shader и easing как установленные факты.

### Этап 2. Контент и визуальная основа

**Skills:** `clone-website`, `frontend-design`. **Оценка:** 0,5–1 день после получения материалов.

- Собрать 3–5 репрезентативных серий для первого прохода: горизонтальные, вертикальные и квадратные фото; затем добавить оставшиеся через тот же manifest.
- Для каждой серии задать `slug`, название, категорию, год, подписи и alt, порядок фото, обложку и focal point. Поля agency/client показывать только при наличии данных.
- Получить имя/логотип, краткое описание, портрет, реальные контакты и язык интерфейса. Допущение для черновика — русский контент и латиница в URL; перед финальной типографикой проверить кириллицу.
- Выбрать разрешённые шрифты с нужными начертаниями и символами; если используются аналоги, зафиксировать визуальное отличие. Не выводить название шрифта из внутреннего CSS-идентификатора.
- Подготовить web-версии фото с responsive-размерами, подходящими для DOM и текстур. Оригиналы высокой детализации держать отдельно от publish artifact.

**Выход:** контент отделён от layout; палитра, шкала типографики, spacing и crop описаны. Отсутствующие материалы обозначены placeholders; визуальная приёмка на placeholders остаётся предварительной.

### Этап 3. Основа приложения и рабочая навигация

**Skills:** `ponytail`, `frontend-design`. **Оценка:** 0,5–1 день.

- Создать Vite + TypeScript scaffold, токены CSS, manifest и hash-навигацию.
- Сделать Header, Footer, Gallery, ProjectView и InfoView в семантическом DOM. Реализовать клики и Back/Forward до анимаций.
- Предусмотреть прямую ссылку на серию, неизвестный slug, empty filter, недоступное изображение и возврат к прежним фильтру/позиции/focus.
- Добавить команды `typecheck` и `build`; зафиксировать lockfile. Не требовать CI до появления рабочего scaffold.

**Выход:** все P0-сценарии проходят с обычными изображениями; сборка и проверка типов успешны.

### Этап 4. Точная статическая вёрстка

**Skills:** `clone-website`, `frontend-design`. **Оценка:** 1–2 дня.

- Перенести измеренные токены, геометрию, пропорции фотографий и поля для каждого представления.
- Проверить Header/Footer, текстовые метаданные, Info, края контейнеров и перекрытия. Удалить случайные browser margins и конфликты CSS specificity.
- Использовать реальные breakpoint из этапа 1. Проверить промежуточные ширины и длинные русские строки.
- Сделать пары screenshots оригинал/локальный сайт с одинаковым viewport, состоянием, загруженными fonts и остановленной анимацией. Замены branding/контента пометить как намеренные различия.

**Выход:** композиция сопоставима без motion; нет случайного horizontal overflow, скачков layout и искажённых aspect ratio.

### Этап 5. Прототип WebGL-галереи

**Skills:** `clone-website`, `ponytail`; [Three.js source](https://github.com/mrdoob/three.js/blob/dev/src/materials/ShaderMaterial.js). **Оценка:** 1,5–3 дня.

- На 3–5 фото создать один canvas и связать плоскости с геометрией DOM. Согласовать crop, цвет и размеры изображения между слоями.
- Реализовать shader с параметрами скорости, направления, силы деформации и затухания. Начать с минимальной модели, затем сравнить её с видеонаблюдением.
- Проверить синхронизацию размеров, DPR, scroll и pointer coordinates. Не принимать красивый, но другой эффект за повторение референса.
- Сохранить работоспособный DOM-вариант при недоступном WebGL2, ошибке инициализации или утрате context. На reduced motion отключать деформацию и избыточные переходы.
- Проверить память, число одновременно загруженных текстур и освобождение ресурсов на повторных открытиях серий.

**Выход:** один основной эффект воспроизведён и измерен до распространения на все фотографии. Допущения shader перечислены в spec. Если прототип выявляет проблему на телефоне, её решение и визуальный компромисс фиксируются до дальнейшей доводки.

### Этап 6. Motion и связанные переходы

**Skills:** `clone-website`, `frontend-design`. **Оценка:** 1,5–3 дня.

- Подключить Lenis и GSAP с единым источником кадров; renderer получает актуальные progress и velocity. Исключить двойной scroll и конкурирующие RAF loops.
- Настроить Overview ↔ List, открытие и закрытие серии, Info, фильтры и счётчики по спецификациям.
- Intro связывать с готовностью критичных ресурсов, предусмотреть timeout и частичную ошибку. Не задерживать доступ ради фиктивного процента.
- Обработать быстрые повторные действия, Back во время перехода, resize/orientation change, сворачивание вкладки и возвращение.
- Добавить custom cursor только если он подтверждён исследованием и доступен для fine pointer. Клавиатура и touch сохраняют полноценный доступ.

**Выход:** переходы воспроизводимы, обратимы и не оставляют scroll lock, невидимый контент или потерянный focus.

### Этап 7. Mobile, доступность и производительность

**Skills:** `frontend-design`, `webapp-testing`. **Оценка:** 1–2 дня.

- Проверить narrow layout, touch scroll, отсутствие hover-зависимостей, safe areas и изменение высоты mobile browser UI.
- Ограничить DPR и детализацию по измеренному frame time; не загружать все крупные фото до первого экрана. Отдельно проверить cold и warm cache.
- Проверить Tab/Shift+Tab, Enter/Space, Escape при закрываемом представлении, восстановление focus и семантику links/buttons. Для отдельного route view не вводить modal focus trap без необходимости.
- Проверить `prefers-reduced-motion`, отсутствие WebGL и ошибки изображений. Контакты доступны во всех поддержанных режимах.
- Выполнить живую проверку Safari на iPhone и Chrome на Android при наличии устройств. Desktop emulation и WebKit automation записывать отдельно, не выдавая за реальный iPhone.

**Выход:** критичные пользовательские сценарии доступны на mobile и при ограничении эффектов. Непроверенные устройства перечислены с конкретным сценарием будущей проверки.

### Этап 8. Приёмка и подготовка GitHub Pages

**Skills:** `webapp-testing`; официальные документы Vite/GitHub. **Оценка:** 0,5–1 день, без ожидания доступа/DNS.

- Выполнить проверки из раздела 8 и визуальную сверку. Сохранить `docs/qa/acceptance.md` с результатами и открытыми отличиями.
- Подготовить Actions workflow: установка из lockfile, typecheck, build, загрузка `dist`, deploy в Pages. Использовать официальную актуальную конфигурацию и нужные permissions.
- Указать `base` для выбранного адреса: `/<repository>/` для project site, `/` для user site или собственного домена. Строить asset URLs с учётом Vite base, включая изображения/текстуры из manifest.
- Перед публикацией подтвердить назначение сайта и материалы; выбрать реальный repository, Pages source и при необходимости домен. Сейчас эти параметры не заданы, публикация не выполняется.
- После deploy открыть реальный адрес и прямую hash-ссылку на серию; проверить refresh, assets, MIME, консоль и Back/Forward. Успешный workflow сам по себе не подтверждает визуальную работу сайта.

**Выход:** опубликованный URL проверен отдельно от localhost, либо явно указано, какая внешняя настройка остаётся невыполненной.

## 8. Проверки и критерии завершения

| Проверка | Что считать результатом |
|---|---|
| `npm ci`, `npm run typecheck`, `npm run build` | Чистая установка из lockfile, отсутствие ошибок типов, создан `dist`; команды появятся на этапе scaffold |
| Production preview | Сценарии работают на готовой сборке, а не только dev server |
| Smoke | Overview/List/фильтры/серия/Info/Close/Back/Forward; прямой hash URL и refresh; быстрые повторные действия |
| Visual QA | Парные снимки 1440, 768 и 390px; сверены композиция, шрифты, crop, расстояния и фиксированные слои; намеренные отличия перечислены |
| Motion QA | Сравнение scroll и переходов по одинаковому сценарию, включая остановку и обратное движение; FPS не подменяет сходство |
| Ошибки | Нет необработанных runtime errors и failed asset requests в проверенном сценарии; отказ фото/WebGL обрабатывается |
| Доступность | Клавиатура, focus, reduced motion и DOM fallback проверены отдельными проходами |
| Real-device QA | Результаты iPhone/Android с указанием модели и browser; если недоступны — критерий остаётся открытым |
| Published smoke | Реальный Pages URL, repository prefix, refresh серии и все assets проверены после deploy |

Browser smoke по `webapp-testing` запускать после появления приложения; helper сначала вызывать с `--help`. Для бесконечной анимации readiness определять также по загрузке fonts/images и готовности приложения, не ждать произвольного sleep. Выбрать один browser harness, не дублировать одинаковые тесты в Python и TypeScript.

Предлагаемые бюджеты, которые следует подтвердить на прототипе: критичная первая загрузка до **3 MB compressed**, desktop около **60 FPS** на зафиксированном устройстве, mobile не ниже **30 FPS** в согласованном основном сценарии. Это проектные цели, **не измерения оригинала и не достигнутые результаты**. Массовую загрузку текстур, decode и длинные main-thread задачи проверять профилем, а не только средним FPS.

Сначала закрыть технические сценарии, затем провести визуальную приёмку пользователем на реальных фотографиях. Build, screenshots или отчёт агента не означают автоматически, что художественное сходство принято.

## 9. GitHub Pages: решения до публикации

GitHub Pages технически размещает нужную статику. Перед публикацией сверить назначение с [ограничениями GitHub](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits): они затрагивают business/e-commerce, транзакции и educational copies. Техническая совместимость не определяет допустимость любого сценария. Подробности — в [заметке платформы](docs/research/platform-notes.md).

Практические решения: собственный код и материалы Xenia, web-версии фото, подсчёт размера и трафика. Лимиты — **1 GB** на сайт и soft bandwidth **100 GB/месяц**. Внешний image CDN добавлять при измеренной потребности. Назначение hosting уточнить до deploy; исходники остаются в GitHub.

## 10. Оценка, зависимости и риски

Предварительная оценка: **8–16 рабочих дней** для одного разработчика с учётом калибровки эффектов. Первый вертикальный прототип — примерно **2–4 дня** после начала реализации и получения минимального набора фото. Фазы частично пересекаются; оценки не являются обещанием срока. Ожидание материалов, доступа и DNS сюда не входит.

Критический путь: полный разбор → контент и токены → DOM-основа → WebGL-прототип → связанные переходы → реальные устройства → визуальная приёмка → опубликованный smoke.

| Риск или неизвестное | Действие |
|---|---|
| Точный shader и easing не установлены | Видеонаблюдение, маленький прототип, явный список аппроксимаций |
| Контент Xenia и точное имя бренда не предоставлены | Начать технический прототип на обозначенных материалах; финальную визуальную приёмку проводить после замены |
| Право использования и реальные названия шрифтов неизвестны | Выбрать разрешённый файл или согласованный аналог, проверить кириллицу |
| Фото перегружают GPU/сеть | Responsive assets, ограничение видимых текстур и DPR, профиль на устройствах |
| Source меняется после исследования | Датированные reference screenshots/video и specs как зафиксированная версия сравнения |
| Нужны clean URLs вместо hash | До завершения routing перейти к генерации статических HTML для всех серий |
| Репозиторий, домен и назначение публикации не определены | Подготовить локальную сборку; внешний deploy закончить после определения параметров |
| Реальный iPhone/Android недоступен | Прямо оставить device acceptance открытой и указать сценарии для ручного прогона |

Неизвестные материалы не препятствуют будущему исследованию и техническому прототипу. Вопросы о бренде, языке, составе серий и финальных контактах собрать вместе перед заменой чернового контента, а не останавливать каждую независимую операцию.

## 11. Следующее действие и текущая проверка

Локальная реализация выполнена по команде пользователя. Следующее действие — визуальная приёмка технической версии, калибровка motion и проверка реальных устройств. Перед публикацией выбрать repository и параметры Pages.

Фактические команды, browser smoke, screenshots, performance snapshots и ограничения перечислены в [docs/qa/acceptance.md](docs/qa/acceptance.md). Реальные устройства, художественное совпадение и опубликованный URL **не проверены, проверить так:** пройти оставшиеся сценарии из конца QA-отчёта. Подготовленный workflow не означает выполненный deploy.
